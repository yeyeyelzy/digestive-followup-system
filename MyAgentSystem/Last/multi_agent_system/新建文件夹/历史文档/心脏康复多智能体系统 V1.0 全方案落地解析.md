## 一、PDF方框乱码问题根因与终极修复方案

### 1.1 核心根因定位

PDF出现全方框/部分方框乱码，**99%的场景为中文字体缺失与未嵌入问题**，剩余为编码格式错误，具体分为两类：

- 图表类乱码：matplotlib绘图时未指定兼容中文的字体，或生成的图片字体未嵌入PDF，渲染时无匹配字体 fallback 为方框；

- 文本类乱码：ReportLab/WeasyPrint等PDF生成库未加载中文字体文件，中文Unicode字符无法正常渲染。

### 1.2 分步可落地修复方案

#### 步骤1：全局统一中文字体配置（解决图表乱码）

在项目全局配置文件`config.py`中新增字体配置，替换所有硬编码字体设置，确保绘图与PDF生成共用一套兼容字体：

```Python

# config.py 全局字体配置
import os
import matplotlib.pyplot as plt
from matplotlib import rcParams

# 项目根目录绝对路径
BASE_DIR = os.path.dirname(os.path.abspath(__file__))
# 字体文件存放路径（项目内打包，避免环境字体缺失）
FONT_DIR = os.path.join(BASE_DIR, "assets", "fonts")
# 强制指定中文字体（推荐开源无版权的思源黑体，随项目打包）
DEFAULT_FONT_FAMILY = "Source Han Sans CN"
DEFAULT_FONT_PATH = os.path.join(FONT_DIR, "SourceHanSansCN-Regular.ttf")

# matplotlib全局绘图字体配置（解决图表中文乱码）
rcParams["font.family"] = [DEFAULT_FONT_FAMILY, "SimHei", "Microsoft YaHei", "Arial Unicode MS", "sans-serif"]
rcParams["axes.unicode_minus"] = False  # 解决负号显示为方框
rcParams["pdf.fonttype"] = 42  # 强制字体嵌入PDF，避免目标环境缺失字体
rcParams["ps.fonttype"] = 42

# PDF生成库全局字体注册（以ReportLab为例）
from reportlab.pdfbase import pdfmetrics
from reportlab.pdfbase.ttfonts import TTFont
if os.path.exists(DEFAULT_FONT_PATH):
    pdfmetrics.registerFont(TTFont(DEFAULT_FONT_FAMILY, DEFAULT_FONT_PATH))
    PDF_DEFAULT_FONT = DEFAULT_FONT_FAMILY
else:
    PDF_DEFAULT_FONT = "Helvetica"  # 兜底兼容
```

#### 步骤2：PDF生成全流程字体嵌入（解决文本乱码）

重构PDF生成逻辑，所有中文文本强制使用已注册的中文字体，示例如下：

```Python

# report_generator/pdf_generator.py 修复后代码
from reportlab.platypus import SimpleDocTemplate, Paragraph, Image
from reportlab.lib.styles import getSampleStyleSheet
from config import PDF_DEFAULT_FONT, BASE_DIR
import os

def generate_pdf_report(content_list, save_path, patient_id, report_date):
    """
    生成带中文字体嵌入的PDF报告
    """
    # 初始化文档
    doc = SimpleDocTemplate(save_path)
    story = []
    styles = getSampleStyleSheet()

    # 强制所有样式使用中文字体
    for style_name in styles:
        style = styles[style_name]
        style.fontName = PDF_DEFAULT_FONT
        if style_name in ["Title", "Heading1", "Heading2"]:
            style.fontName = PDF_DEFAULT_FONT
            style.leading = 20  # 解决中文行高重叠

    # 标题与内容渲染
    story.append(Paragraph(f"患者{patient_id} {report_date} 健康监测报告", styles["Title"]))
    for content in content_list:
        if isinstance(content, str):
            story.append(Paragraph(content, styles["BodyText"]))
        elif isinstance(content, Image):
            story.append(content)
    
    # 生成PDF（自动嵌入已注册字体）
    doc.build(story)
    return save_path
```

#### 步骤3：兜底兼容方案

1. 随项目打包开源中文字体文件（思源黑体/微软雅黑），避免不同服务器环境字体缺失；

2. 生成PDF前做字体校验，无对应字体时自动 fallback 到系统兼容字体，同时输出警告日志；

3. 所有可视化图表先保存为PNG图片（带中文渲染完成），再嵌入PDF，避免矢量图字体丢失。

### 2.2 场景2：若依框架集成方案（Python/Java双版本适配）

若依框架分为**Python版（基于FastAPI）** 和**主流Java版（基于SpringBoot）**，分别提供适配方案，支持随框架一起启动、数据双向传递。

#### 2.2.1 适配方案1：若依Python版（FastAPI）无缝集成

1. **集成方式**：将多智能体系统作为若依Python版的一个业务模块，直接import到项目中，共用框架的权限体系、数据库、定时任务。

2. **集成步骤**：

    - 步骤1：将整个多智能体项目文件夹复制到若依Python版的`modules/`目录下，重命名为`cardiac_rehab`；

    - 步骤2：在若依的`requirements.txt`中添加本项目的依赖包，执行安装；

    - 步骤3：修改本项目`config.py`中的路径配置，适配若依的项目目录，将输入输出目录映射到若依的`static/`目录，方便前端访问；

    - 步骤4：在`cardiac_rehab/`目录下新增`api.py`，编写接口路由，注册到若依的路由系统中；

    - 步骤5：在若依的`admin.py`中注册定时任务，实现每日凌晨自动生成日报、每周生成周报。

3. **启动方式**：随若依Python版的启动命令`python app.py`一起启动，无需单独启动服务。

4. **数据传递**：直接通过函数调用传递数据，示例如下：


#### 2.2.2 适配方案2：若依Java版（SpringBoot）跨语言集成

提供3种稳定可行的集成方式，优先推荐**HTTP微服务方式**（兼容性最强、解耦最彻底）。

##### 方案A：HTTP微服务集成（优先推荐）

1. **部署方式**：将多智能体系统打包为独立的Python微服务（基于FastAPI），与若依Java服务部署在同一服务器/集群内；

2. **随框架启动配置**：

    - Linux环境：在若依Java的启动脚本`start.sh`中添加Python服务启动命令，实现一键启动；

    ```Shell

    echo "启动心脏康复多智能体微服务..."
    nohup python3 /opt/ruoyi/cardiac_rehab_agent/app.py > /opt/ruoyi/logs/agent.log 2>&1 &
    echo "智能体服务启动完成，开始启动若依后端..."
    # 原有若依Java启动命令
    nohup java -jar ruoyi-admin.jar > /opt/ruoyi/logs/ruoyi.log 2>&1 &
    ```

    - Windows环境：编写批处理脚本，先启动Python服务，再启动若依Java jar包。

3. **数据传递**：Java服务通过`RestTemplate`/`FeignClient`调用Python微服务的HTTP接口，传递JSON格式数据，接收返回结果，示例如下：


1. **权限适配**：Python微服务接口集成若依的Token鉴权，所有请求必须携带若依生成的Token，校验通过后方可执行。

##### 方案B：Py4J跨语言调用（适合低频小数据量场景）

1. **实现原理**：通过Py4J实现Java虚拟机与Python解释器的双向通信，Java直接调用Python的函数方法；

2. **适配方式**：Python端启动Py4J网关服务，Java端引入Py4J依赖，直接调用智能体核心函数；

3. **启动方式**：同方案A，随若依启动脚本一起启动Py4J网关服务。

##### 方案C：容器化编排部署（适合生产环境）

1. **实现方式**：将多智能体Python服务打包为Docker镜像，若依Java服务也打包为镜像，通过Docker Compose统一编排，实现一键启停、服务发现、自动重启；

2. **优势**：环境隔离、不依赖服务器本地Python环境、扩缩容方便，与若依框架完全解耦。

### 2.4 场景4：文件夹监听式外部调用入口

适合离线批量处理、第三方系统无接口对接场景，通过监听指定文件夹，自动触发智能体流程，无需人工干预。

#### 2.4.1 实现方案

基于Python的`watchdog`库实现文件夹监听，核心规则如下：

1. 监听目录：`data/listen/input/`，分为`pending/`（待处理）、`processing/`（处理中）、`success/`（处理成功）、`fail/`（处理失败）4个子目录；

2. 触发条件：当`pending/`目录下新增符合命名规范的ZIP压缩包（命名格式：`patient_患者ID_数据周期.zip`），自动触发处理流程；

3. 处理流程：解压压缩包→校验数据格式→移动到processing目录→执行智能体全流程→生成报告→输出到`data/listen/output/`目录→源文件移动到success目录；

4. 异常处理：校验失败/处理失败，源文件移动到fail目录，生成错误日志，不影响后续文件处理。

#### 2.4.2 监听入口核心代码

```Python

# listen_service.py 文件夹监听服务入口
import os
import time
import zipfile
from watchdog.observers import Observer
from watchdog.events import FileSystemEventHandler
from config import BASE_DIR
from main import process_single_patient_data
from utils.logger import setup_logger

logger = setup_logger("folder_listen", os.path.join(BASE_DIR, "logs", "listen_service.log"))

# 监听目录配置
LISTEN_BASE_DIR = os.path.join(BASE_DIR, "data", "listen")
PENDING_DIR = os.path.join(LISTEN_BASE_DIR, "input", "pending")
PROCESSING_DIR = os.path.join(LISTEN_BASE_DIR, "input", "processing")
SUCCESS_DIR = os.path.join(LISTEN_BASE_DIR, "input", "success")
FAIL_DIR = os.path.join(LISTEN_BASE_DIR, "input", "fail")
OUTPUT_DIR = os.path.join(LISTEN_BASE_DIR, "output")

# 初始化目录
for dir_path in [PENDING_DIR, PROCESSING_DIR, SUCCESS_DIR, FAIL_DIR, OUTPUT_DIR]:
    os.makedirs(dir_path, exist_ok=True)

class DataFileHandler(FileSystemEventHandler):
    def on_created(self, event):
        # 仅处理zip压缩包，忽略临时文件
        if not event.is_directory and event.src_path.endswith(".zip"):
            file_name = os.path.basename(event.src_path)
            logger.info(f"监听到新增数据文件：{file_name}")
            # 等待文件写入完成，避免文件未写完触发处理
            time.sleep(2)
            self.process_file(event.src_path, file_name)

    def process_file(self, file_path, file_name):
        try:
            # 1. 解析患者ID与数据周期
            if not file_name.startswith("patient_"):
                raise Exception("文件命名不符合规范，格式应为patient_患者ID_数据周期.zip")
            name_split = file_name.replace(".zip", "").split("_")
            patient_id = name_split[1]
            period = name_split[2] if len(name_split)>=3 else "default"

            # 2. 移动到处理中目录
            processing_file_path = os.path.join(PROCESSING_DIR, file_name)
            os.rename(file_path, processing_file_path)

            # 3. 解压文件
            unzip_dir = os.path.join(PROCESSING_DIR, f"{patient_id}_{period}")
            with zipfile.ZipFile(processing_file_path, 'r') as zip_ref:
                zip_ref.extractall(unzip_dir)
            logger.info(f"文件解压完成，患者ID：{patient_id}")

            # 4. 调用核心处理逻辑
            result = process_single_patient_data(patient_id, unzip_dir, os.path.join(OUTPUT_DIR, patient_id))
            if result["code"] != 200:
                raise Exception(result["msg"])

            # 5. 处理成功，移动源文件到success目录
            os.rename(processing_file_path, os.path.join(SUCCESS_DIR, file_name))
            logger.info(f"患者{patient_id}数据处理完成，报告已生成")

        except Exception as e:
            logger.error(f"文件处理失败：{file_name}，错误信息：{str(e)}", exc_info=True)
            # 处理失败，移动文件到fail目录
            fail_file_path = os.path.join(FAIL_DIR, file_name)
            if os.path.exists(processing_file_path):
                os.rename(processing_file_path, fail_file_path)
            elif os.path.exists(file_path):
                os.rename(file_path, fail_file_path)
            # 生成错误日志文件
            with open(os.path.join(FAIL_DIR, f"{file_name}.error.log"), "w", encoding="utf-8") as f:
                f.write(f"处理时间：{time.strftime('%Y-%m-%d %H:%M:%S')}\n错误信息：{str(e)}")

if __name__ == "__main__":
    event_handler = DataFileHandler()
    observer = Observer()
    observer.schedule(event_handler, PENDING_DIR, recursive=False)
    observer.start()
    logger.info(f"文件夹监听服务已启动，监听目录：{PENDING_DIR}")
    try:
        while True:
            time.sleep(1)
    except KeyboardInterrupt:
        observer.stop()
    observer.join()
```

启动方式：`python listen_service.py`，支持后台守护进程运行，随服务器开机自启。

## 四、接口规范与文档规范详细补充

### 4.1 接口设计总原则

1. **医疗合规性**：所有接口必须做鉴权校验，患者数据加密传输，全操作留痕可审计，符合《医疗卫生机构网络安全管理办法》；

2. **RESTful规范**：所有接口遵循RESTful设计风格，URL语义清晰，请求方式与业务动作匹配（GET查询、POST新增/执行、PUT修改、DELETE删除）；

3. **幂等性**：所有写操作接口必须保证幂等性，重复调用不会产生重复数据、重复执行流程；

4. **容错性**：接口异常时返回统一格式的错误信息，不抛出堆栈信息，不导致服务崩溃；

5. **兼容性**：接口版本号管理，后续迭代不影响历史版本接口的正常使用。

### 4.2 统一数据交互规范

#### 4.2.1 统一请求/响应格式

1. **请求格式**：所有POST/PUT请求采用JSON格式，编码为UTF-8，请求头必须携带`Content-Type: application/json`、`Authorization: Bearer {token}`；

2. **统一响应格式**：

```JSON

{
    "code": 200, // 状态码：200成功，非200失败
    "msg": "操作成功", // 提示信息
    "data": {}, // 核心返回数据，成功时返回，失败时可为null
    "requestId": "req_20240520120000001" // 请求唯一ID，用于日志追溯
}
```

1. **时间格式规范**：所有时间字段统一采用`YYYY-MM-DD HH:MM:SS`格式，时区为东八区（UTC+8）；

2. **分页查询规范**：所有分页接口统一采用`pageNum`（页码，从1开始）、`pageSize`（每页条数）作为请求参数，返回数据包含`total`（总条数）、`pages`（总页数）、`list`（数据列表）。

#### 4.2.2 统一错误码体系

|错误码区间|错误类型|说明|
|---|---|---|
|200|成功|接口调用成功|
|4000-4999|请求参数错误|参数缺失、格式错误、不符合规范|
|5000-5999|业务逻辑错误|数据处理失败、智能体执行失败、报告生成失败|
|6000-6999|权限与鉴权错误|Token失效、无权限访问、IP白名单限制|
|7000-7999|服务器内部错误|服务异常、依赖缺失、IO错误|
