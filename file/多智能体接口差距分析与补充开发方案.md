# 多智能体接口差距分析与补充开发方案（基于现有代码与接口文档）

> 日期：2026-03-14  
> 范围：
> - 多智能体实现代码：`MyAgentSystem/multi_agent_system_v2` 与 `MyAgentSystem/Last`
> - 接口规范文档：`MyRuoYi/dev/接口/3D心脏孪生体接口规范.md`、`MyRuoYi/dev/接口/康复成就模块接口规范.md`、`MyRuoYi/dev/接口/其它接口设计意见.md`

---

## 1. 现状结论（先给结论）

当前多智能体系统**具备数据读取与多端报告生成能力**，但与接口文档要求相比，仍是“能力存在、接口未对齐”的状态：

1. 已具备：
- 三类端（患者/家属/医生）的日报、周报、月报输出。
- 心率、活动、睡眠等基础指标统计与可视化数据。
- 医生端结构化报告与康复建议基础框架。

2. 未满足/不完整：
- 未形成文档要求的心脏孪生体实时/预测接口字段形态（`timestamp/heartRate/riskLevel/anomalyFeatures`、`monthIndex/recoveryTrend`）。
- 未形成康复成就“布尔判定接口 + 若依聚合返回”完整链路。
- 患者ID仍主要使用 `P_001/P_002/P_003`，未与数据库中的 `10/11/12` 做统一映射。
- 医生可编辑康复方案、患者/家属查看“智能体原始方案 + 医生修订方案”的双版本能力未落地。
- 风险预测模块缺少“心率预警分类占比 + 文本化解释”等规范字段。

结论：**当前输出不能直接满足三个接口设计文档，需要补充接口适配层、ID映射层、成就判定与方案版本化能力。**

## 3. 对三份接口文档的逐项适配判断

## 3.1 3D心脏孪生体接口规范

### 当前可满足（部分）
- 有心率和风险相关计算基础。
- 有三端逻辑（patient/family/doctor）可复用。

### 当前不满足（关键）
1. 缺少标准接口：
- `/system/heart-twin/realtime`
- `/system/heart-twin/forecast`
- `/api/family/patient/heart-twin/realtime`
- `/api/family/patient/heart-twin/forecast`

2. 缺少规范字段映射：
- 实时：`timestamp`、`heartRate`、`riskLevel`、`anomalyFeatures`
- 预测：`monthIndex`、`monthLabel`、`heartRate`、`riskLevel`、`recoveryTrend`

3. 风险枚举未统一：
- 应统一为 `low/medium/high`。

4. 缺少家属绑定校验逻辑（此项按文档应由若依实现，但多智能体需提供可透传 patientId 的稳定输出结构）。

## 3.2 康复成就模块接口规范

### 当前可满足（部分）
- 已具备读取饮食、行为、用药、生活等原始数据能力，可支持综合判定输入。

### 当前不满足（关键）
1. 缺少智能体判定接口：
- `POST /ai/recovery/healthy-life-decision`
- 返回 `isHealthyLife: boolean`

2. 缺少与若依聚合链路的数据契约：
- 未定义 `healthy_today` 映射规则。
- 未提供“失败回退缓存值”所需的可缓存结构（如判定时间、判定依据摘要、source）。

## 3.3 其它接口设计意见

### 当前可满足（部分）
- 已有“日报/周报/月报”框架，满足“指标变化模块”的基础骨架。
- 已有医生端结构化报告雏形。

### 当前不满足（关键）
1. 风险预测模块不完整：
- 缺少“心率分布图数据结构（可直接画图的数据桶）”。
- 缺少“心率预警分类占比（红/黄/生理性/病理性）”。
- 缺少医生端更专业文本（病因推断、证据链、建议优先级）标准化输出。

2. 康复方案模块不完整：
- 缺少“医生可编辑方案”。
- 缺少“患者/家属同时看到智能体原始方案 + 医生修订方案”。

3. 患者ID约束不满足：
- 患者/家属接口要求带 patientId，并期望使用 10/11/12。

## 4. 缺失补充开发方案（可直接执行）

## 4.1 总体设计

采用“若依BFF + 智能体服务内聚能力”的双层方案：

1. 智能体服务（Python）新增 AI 内部接口：
- `POST /ai/heart-twin/realtime`
- `POST /ai/heart-twin/forecast`
- `POST /ai/recovery/healthy-life-decision`
- `POST /ai/risk/predict`
- `POST /ai/rehab/plan/generate`
- `POST /ai/rehab/plan/revise`（医生修订）

2. 若依服务（Java）新增对外聚合接口：
- 按文档暴露患者端/家属端路径。
- 负责 token 鉴权、角色校验、家属绑定校验、ID解析。
- 调用智能体接口并组装统一响应 `code/msg/data`。

3. ID映射层（必须先落地）：
- 新增映射表：`patient_mapping`  
  - `biz_patient_id`（10/11/12）  
  - `agent_patient_id`（P_001/P_002/P_003）
- 智能体内部仍可保留 P_ 前缀，外部统一使用 10/11/12。

## 4.2 接口契约补齐（字段级）

### A. 心脏孪生体实时

输入：
```json
{
  "patientId": "10",
  "scene": "patient|family",
  "source": "ruoyi"
}
```

输出：
```json
{
  "timestamp": "2026-03-14 10:00:00",
  "heartRate": 96,
  "riskLevel": "medium",
  "anomalyFeatures": ["心动过速倾向", "活动后恢复偏慢"]
}
```

实现要点：
1. `timestamp`：取最近有效心率样本时间。
2. `heartRate`：最近5-15分钟平滑值。
3. `riskLevel`：统一映射为 `low/medium/high`。
4. `anomalyFeatures`：由规则引擎 + 医学知识库生成短语列表。

### B. 心脏孪生体预测（1-3月）

输出：
```json
[
  {"monthIndex":1,"monthLabel":"1个月后","heartRate":92,"riskLevel":"medium","recoveryTrend":"stable"},
  {"monthIndex":2,"monthLabel":"2个月后","heartRate":84,"riskLevel":"low","recoveryTrend":"improve"},
  {"monthIndex":3,"monthLabel":"3个月后","heartRate":78,"riskLevel":"low","recoveryTrend":"improve"}
]
```

实现要点：
1. 基于近30天趋势 + 依从性评分 + 康复计划执行度进行外推。
2. `recoveryTrend` 枚举固定：`improve/stable/worse`。

### C. 健康生活布尔判定

输入：饮食/行为/服药/生活/生命体征等。
输出：
```json
{
  "patientId": "10",
  "date": "2026-03-14",
  "isHealthyLife": true,
  "score": 0.84,
  "reasons": ["按时服药", "步数达标", "睡眠达标"]
}
```

说明：
- 对外文档强制字段是 `isHealthyLife`，`score/reasons` 可作为若依缓存与排障依据。

### D. 康复方案版本化

新增数据结构：
```json
{
  "planId": "RP_10_20260314",
  "patientId": "10",
  "aiPlan": {"content":"..."},
  "doctorRevisedPlan": {"content":"...", "revisedBy":"doctor_001", "revisedAt":"2026-03-14T09:30:00"},
  "version": 2,
  "status": "doctor_revised"
}
```

患者端/家属端展示：
- `aiPlan`
- `doctorRevisedPlan`（存在时优先展示）

## 4.4 开发顺序（两周可落地）

### 第1阶段（D1-D3）：接口骨架与ID映射
1. 建立 `10/11/12 <-> P_001/P_002/P_003` 映射表与转换服务。
2. 落地 3 个 AI 内部接口：realtime、forecast、healthy-life-decision（先返回可计算版本）。
3. 若依打通最小链路（患者端 realtime/forecast）。

### 第2阶段（D4-D7）：字段对齐与质量提升
1. 完成 `riskLevel`、`recoveryTrend` 枚举统一。
2. 增加 anomalyFeatures、预警分类占比、文本化解释。
3. 若依家属端接口加入绑定校验。

### 第3阶段（D8-D10）：康复方案版本化
1. 增加 `aiPlan + doctorRevisedPlan + version` 存储。
2. 医生端修订接口与审计字段。
3. 患者/家属查询接口返回双版本。

### 第4阶段（D11-D14）：联调与验收
1. 联调前端字段；保留失败回退模拟数据机制。
2. 压测与异常场景（无数据、接口超时、权限失败）。
3. 发布验收报告。

## 4.5 验收标准（必须全部通过）

1. 患者ID对齐：前端与若依全部使用 10/11/12；智能体内部可保留 P_ 前缀。
2. 四个心脏孪生体接口返回字段与枚举完全符合文档。
3. 康复成就：
- 智能体返回 `isHealthyLife:boolean`
- 若依聚合返回 `healthy_today` 与成就字段
4. 风险预测：
- 提供风险等级
- 提供心率分布与预警占比数据
- 提供文本性医学解释
5. 康复方案：
- 医生可修改
- 患者/家属可同时查看 AI 原方案与医生修订方案
6. 错误码与容错：符合文档中的 200/400/401/403/404/500 行为。

---

## 5. 风险与注意事项

1. 风险等级统一口径：历史代码中存在“中文风险等级”和“英文枚举”混用，需统一在网关层收敛。
2. 时间语义：实时接口应明确“采样时间”而非“接口响应时间”。
3. 缓存策略：健康成就判定建议按“患者+日期”缓存，避免重复计算。
4. 法规合规：医生端文本建议保留“AI生成，需临床确认”标识。

---

## 6. 结论

现有多智能体系统的“数据与分析能力”可复用度较高，但“接口契约、ID规范、聚合链路、版本化能力”尚未达标。按本方案补齐后，可以较平滑对接你在若依侧的接口设计，并支撑患者/家属/医生三端一致的线上行为。
